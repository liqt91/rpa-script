② 主线判断 最关键的取舍

结论：主线的「产品形态」是 —— DSh 里的 RPA 工具

最近两周所有实质推进（rpa_capture、elements.json 拆分、项目模式 CRUD、rpa_bridge 免后端读写）都发生在「把 RPA 能力以 DSH 原生态交付」这条线上。它不是巧合，是产品被真实使用后自然长出来的主线。

为什么是这条线

  • 你实际在用：从对话到流程 tab 到捕获，全流程都在 DSH 内完成，编辑免后端、捕获免后端
  • 价值密度最高：捕获 + 工作流编排 + 运行这三件事，DSH 给了最短路径，独立平台反而多一层
  • 独立平台是「底座」而非「目标」：后端/扩展/编辑器仍是 DSH 工具背后的能力层，可保留但不需单独打磨 UI
  • Electron 壳 / webrpa / tdSelector 应明确退出主线：不投入、不维护、仅作参考
1
收敛产品定位
明确为「面向 DSH 用户的浏览器 + 桌面自动化工具」。所有功能决策先问一句：它让 DSH 里的使用更顺吗？不满足就降级或搁置。
2
独立平台降级为可复用底座
后端/扩展/编辑器保留，但不再单独规划独立站 UI 的增强；把精力引流到 DSH 侧入口与体验。
3
外围资产明确归属
webrpa/、tdSelector_1.2.7 → 参考目录，不进版本主线；MCP server 保留但标注「可选旁路」；Electron 壳标记「搁置」。

⑤ 开发流程 / 工程化收口 减少手工，提升可复现

痛点

  • 前端产物双副本：build 后要手动 robocopy /MIR 到 profiles/web/rpa-dsh-plugin 和 node_modules/... 两处
  • 插件 lib 三处：repo / 两 profile 副本，改一处易漏
  • 后端改动重启才生效，捕获类改动 spawn 新进程即时生效（两者易混淆）
  • 无统一 dev 命令，现有 run-build.cjs 只覆盖部分

收口方案

  • 建一个 scripts/sync-plugin.js：build + 同步两处 static + 同步三处 lib，一条命令完成
  • harness:check 纳入「改动必须过」门槛（已有结构检查，保持）
  • 测试基座一次性修复 Host 白名单那 8 个 error，让 pytest 全绿作为回归基线
  • README / AGENTS.md 同步到现状，避免后续 agent 再被过时文档误导

⑥ 需要你拍板的决策点 决定后即可动工

1. 主线确定为「DSH 里的 RPA 工具」？
若同意 → 独立平台 UI 不再单独投入；若你其实想做独立产品，则主线要重排（影响 P1-P3 全部）。
2. 独立跑面（Electron / MCP / webrpa）如何处置？
建议：Electron 搁置、webrpa & tdSelector 移出仓库根、MCP 留作可选旁路并在文档标注。
3. 旧平台功能（AI 生成 / 定时调度）优先级是否下移？
建议：AI 生成重写为「对话内生成」进 P1；定时调度降为「确有需要再做」。若你想要，可恢复原优先级。
4. 是否立刻动手做「工程化收口 + 主线段落」？
建议：先做 ①doc 同步 + ②测试基座修复 + ③sync-plugin.js，三者小、收益大；再做 P1 的 UX 补强。
