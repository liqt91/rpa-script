# 工作日志 2026-08-14

## 一、捕获期间普通点击被全键屏蔽 — 只吞捕获手势

用户报告：桌面捕获（新）执行时，捕获期间**普通左键点击也被屏蔽**了，期望只有
Alt+点击（捕获手势）的点击被吞掉。

### 根因

`_install_mouse_swallow_hook()` 的 `_cb` 对 `_SWALLOW_MOUSE_MSGS`（L/R/M 键
down/up）**全部** `return 1` 吞掉，没有区分手势与普通点击。

### 修复（overlay.py）

- 新增 `_SWALLOW_GESTURE_DOWN_UP`（down 码 → 配对 up 码）：只吞 **Alt+左键=捕获**、
  **右键=取消** 两个手势的 down/up 对。
- 普通左键/中键：仅记录按住状态（供 `_mouse_down` 判断模态态），`CallNextHookEx`
  透传给应用 —— 捕获期间可正常操作目标应用。
- 吞掉 down 后对应 up 也吞（`swallowed_ups` 闭包集合），防孤立 up 落到应用。
- 吞 down 时若 Alt 已松开（先松 Alt 后松键），up 仍按配对吞掉。

## 二、捕获执行/alt+click 卡顿 — 全局钩子串行化整机鼠标 + hover 每帧抢锁

用户报告：捕获执行时有点卡顿，alt+click 时也卡顿。

### 根因（两条）

1. **alt+click 卡顿（主因）**：`WH_MOUSE_LL` 是全局钩子，整机鼠标输入被串行化到
   本线程消息泵。alt+click 确认后主线程阻塞在 `_build_element_info`（UIA 枚举最长
   3s + 截图），**期间整机鼠标全部冻结**；同时 hover worker 还在并发查 UIA，
   相互拖慢（XAML 应用深搜 1-5s 时明显）。
2. **hover 卡顿**：`run_capture`（浮窗模式）每帧**无条件**抢 `_uia_draw_lock`
   （超时 50ms）。worker 深搜期间每帧都白等 50ms → 帧率骤降。`overlay_mask.py`
   已有 `needs_update` 无锁预检，浮窗模式漏了同样的优化。

### 修复

- **手势确认即卸载钩子**（`run_capture` / `run_capture_mask` 两处）：alt+click 或
  右键确认后，先 `_uninstall_mouse_swallow_hook()` 再进入慢的 UIA 枚举/截图 ——
  主线程后续阻塞不再冻结整机鼠标（浮窗模式额外显示"捕获中..."提示）。
- 新增 `_finalize_capture(hwnd, x, y)` 收尾辅助（两模式共用）：暂停 hover worker
  （避免与 `_build_element_info` 的 UIA 查询并发打满 provider）、有界等鼠标松开
  （改用 `GetAsyncKeyState`，钩子已卸载后物理按键状态恢复可靠）、尽力等 worker
  当前查询结束（`_uia_draw_lock.acquire(timeout=0.5)` 持锁期间 worker 无法再查询）。
- **hover 无锁预检**（浮窗模式）：只有高亮 rect 或悬浮框文本确实需要变化时才抢
  `_uia_draw_lock`，与 `overlay_mask.needs_update` 思路一致。

### 涉及文件

| 文件 | 改动 |
|---|---|
| `scripts/capture_gui/overlay.py` | 钩子只吞捕获手势（`_SWALLOW_GESTURE_DOWN_UP` + `swallowed_ups`）、`_finalize_capture` 新增、`run_capture` hover 无锁预检、alt+click 先卸钩子 |
| `scripts/capture_gui/overlay_mask.py` | alt+click/右键确认后先卸钩子，收尾统一走 `ov._finalize_capture` |

## 三、遮罩模式（desktop_mask）鼠标移动卡 — 钩子移入独立泵消息线程

用户反馈：alt+click 不卡了，但进入「捕获桌面元素新」（全屏遮罩）模式后，**鼠标移动
还是有卡的感觉**。

### 根因

`WH_MOUSE_LL` 是全局钩子，低级钩子回调运行在**安装它的线程**上 —— 原来装在主循环
线程，主循环一阻塞（遮罩全屏位图重绘 + `UpdateLayeredWindow` + `SetWindowRgn` 触发
DWM 重排、`_uia_draw_lock` 锁等待等，单次 10-50ms，鼠标移动时高亮频繁变化反复触发），
整机鼠标输入就被串行化冻结 → 光标移动一顿一顿。

### 修复（overlay.py）

- 钩子改装在**独立泵消息线程**（`_hook_pump`）：线程内 `SetWindowsHookExW(WH_MOUSE_LL)`
  + 阻塞式 `GetMessage` 泵取（低级钩子消息投递到安装线程队列），回调在泵线程即时执行。
  - 主循环怎么阻塞（遮罩重绘/UIA/锁等待）都不再影响系统鼠标 —— 光标始终流畅。
  - 主循环只读钩子维护的手势状态（`_consume_mouse_click`/`_mouse_down`，`_mouse_hook_lock`
    保护），语义不变。
  - 安装握手：`threading.Event` + 结果回传；卸载：`UnhookWindowsHookEx` +
    `PostThreadMessageW(WM_QUIT)` 唤醒阻塞中的 `GetMessage`（新增 `_GetMessageW`/
    `_PostThreadMessageW`/`_GetCurrentThreadId` 声明）。
- 主循环 `_pump_messages()` 不再依赖钩子消息（注释同步更新）；遮罩窗/悬浮窗的
  `WM_GETOBJECT`/`WM_NCHITTEST` 仍由主循环泵取，行为不变。

## 五、hover 框到 tab、alt+click 却捕获整窗 — 捕获复用 worker 结果

用户反馈：框选 Windows PowerShell 的 tab 元素没问题，但 alt+click 后捕获的是整个
PowerShell 窗口。

### 根因

hover 高亮与捕获走**两套独立的 UIA 查询**：

- **hover**（`_uia_hit_rect`，跑在 worker 常驻线程，**无超时**）：ControlFromPoint 命中
  整窗 → 深搜兜底慢慢算（XAML 应用 1-5s）→ 最终框出 tab。
- **捕获**（`_try_uia_capture`，新线程 + **3s join 超时**）：同样的深搜在 PowerShell 的
  XAML 树上一慢（实测可 >3s）就被超时杀掉 → 返回 None → `_build_element_info` 降级成
  仅 Win32 → 捕获整窗。

即 worker **已经算好了 tab 的信息**，捕获却另起炉灶重查一遍还超时。

### 修复（overlay.py）

- **worker 缓存完整捕获信息**：`_uia_hit_rect` 改为返回 `(rect, info)` —— 深搜时
  `_deepest_uia_element` 本就把 (best_dict, path) 算出来了，之前只取 rect 丢弃了 info；
  新增 `_deep_info_to_capture()` 转成与 `_try_uia_capture` 同构的 dict（name/control_type/
  automation_id/rect/path/target_index）。节流缓存 `_deep_cache` 同步存 info。
- **info 与显示的高亮配对**：`_HoverWorker._query` 里滞回保留旧 rect 时，info 也用旧
  结果的 —— 保证"显示什么就捕获什么"，不会出现"高亮 tab、信息却是整窗"。
- **捕获优先复用 worker 结果**：`_build_element_info` 先 `_latest_worker_uia_info(x, y)`
  （结果存在、含完整 path、矩形包含捕获点才采纳），没有再走 `_try_uia_capture`。
  - XAML 应用：worker 已算好 → 捕获瞬时完成且与高亮一致（不再超时降级整窗）。
  - 普通应用：worker info 为 None → 走快速链查询，秒回。
- **兜底放宽**：`_UIA_QUERY_TIMEOUT` 3.0 → 8.0s（worker 结果缺失的边缘情况；深搜本身
  有 max_nodes 预算必终止，微信族卡死由 `_is_skip_uia` 负责）。

### 涉及文件

| 文件 | 改动 |
|---|---|
| `scripts/capture_gui/overlay.py` | `_uia_hit_rect` 返回 (rect, info)、`_deep_info_to_capture`、`_HoverWorker` 缓存 info（含滞回配对）、`_latest_worker_uia_info`、`_build_element_info` 复用 worker 结果、`_UIA_QUERY_TIMEOUT` 8s |

## 六、点击后 Windows Terminal/PowerShell 上高亮消失 — 遮罩周期重新置顶

用户反馈：进入新桌面元素捕获（遮罩）模式后，**点击** Windows PowerShell 后其上的选框
（高亮）会消失，其他窗口不会；猜测是 PowerShell 强制置顶。

### 根因

Windows Terminal / PowerShell 等应用在**点击/聚焦时会把自己设为 TOPMOST**，盖到全屏
遮罩（或浮窗高亮框）上方 → 遮罩/高亮被它挡住看不见。其他窗口不这么做，所以只有它
出现"选框消失"。确认：遮罩创建时是 `WS_EX_TOPMOST`，但应用之后把自己置顶就会盖过它，
且"点击后不动鼠标"时遮罩不会重绘，高亮一直藏在下面。

### 修复

- **`_MaskLayer.keep_topmost()`**（overlay_mask.py）：`SetWindowPos(HWND_TOPMOST,
  NOMOVE|NOSIZE|NOACTIVATE)` 把遮罩重新置顶；新增 `_SetWindowPos` 声明（`HWND_TOPMOST`
  必须是指针宽的 -1，不能传 c_int）。
- **遮罩重绘后置顶**：`mask.show()` 绘制完成顺带 `keep_topmost()`（移动鼠标时恢复）。
- **主循环周期置顶**（0.5s 节流）：覆盖"点击后不动鼠标"的场景，应用一旦把自己置顶，
  半秒内遮罩拉回。
- **浮窗模式同步**（overlay.py）：新增 `_keep_border_topmost()`，`run_capture` 主循环
  同样 0.5s 节流置顶 `RpaBorder` 高亮框（同类问题，一并修；该浮窗部分已于第七节随旧
  浮窗捕获模式一并移除）。

## 七、桌面捕获自动路由网页元素 + 移除旧浮窗捕获（方案A落地）

用户确认方向：方案A（桌面捕获识别浏览器内容区自动转网页捕获），前端入口暂不合并；
同时移除旧的「捕获桌面元素」浮窗按钮/功能（新遮罩模式已可用）。

### 背景：为什么需要路由

浏览器有两层：**外壳**（标签栏/地址栏/工具栏，UIA 原生可见）与**页面 DOM**（内容区，
UIA 树里没有，只有扩展 content script 能拿到 css/xpath）。桌面捕获（UIA）落在页面
内容区只能得到整窗渲染宿主，对定位具体网页元素无用；只有扩展能产出真正的 web 元素。

### 修复/改动

- **`overlay.py`**
  - 新增 `_top_window_of` + `_web_capture_target(hwnd, x, y)`：沿父链上溯顶层窗口，
    判定是否**真实浏览器**（chrome/edge/firefox）且点击在**内容区**（顶栏
    `BROWSER_CHROME_HEIGHT=88px` 以下）→ 返回顶层浏览器窗口供委托。
  - `run_capture` 重构：**web 专用**（委托扩展 DOM 拾取）+ 非 web 模式统一委托
    `run_capture_mask`（延迟导入避免循环）；**删除旧浮窗桌面捕获循环**（含
    `_select_hwnd`/`_build_info_text`/Alt+1/2 层级导航/`_keep_border_topmost` 等死代码）。
  - **修复网页捕获回归**：旧代码在 web 分支也装了吞点击钩子 —— 扩展的网页捕获靠页面
    DOM click 事件确认（`onCaptureClick` + altKey），钩子把 Alt+点击在系统层吞掉后
    DOM click 不触发 → 网页捕获确认失效（8/13 加钩子起遗留）。web 分支不再装钩子。
- **`overlay_mask.py`**：新增 `_capture_or_delegate()` —— Alt+点击落在浏览器内容区 →
    隐藏遮罩后委托 `ov._capture_via_extension(web_only=False)`（产出 web 元素 css/xpath，
    与「捕获网页元素」一致）；扩展报 `backToDesktop`（用户点到浏览器外）→ 重建遮罩 +
    重装吞点击钩子，继续桌面拾取。外壳控件/非浏览器维持 UIA/Win32 捕获。
- **`capture_once.py`**：模式清理 —— `web` → `run_capture("web")`；其余 →
    `run_capture_mask("desktop")`；默认 `desktop_mask`。
- **`CaptureToolModal.jsx`**：移除旧「捕获桌面元素」浮窗按钮，遮罩按钮更名「捕获桌面
  元素」（title 注明浏览器内容区自动转网页）；帮助文案同步。重建前端静态资源并清理
  assets 目录 191 个历史构建残留。

### 交互效果

一个「捕获桌面元素」入口：hover 普通应用 → 遮罩框选 → UIA 元素；hover 浏览器顶栏 →
UIA 桌面元素（标签/地址栏）；hover 浏览器页面内容 → Alt+点击自动进入网页 DOM 拾取 →
web 元素（css/xpath）；点到浏览器外自动切回桌面拾取。

## 八、方案A 体验重设计 — hover 自动切换网页拾取（去掉两次点击的割裂）

用户反馈方案A 落地后体验割裂：
1. 网页内 Alt+click 仍捕获 UIA（路由未触发）。
2. 第一次 Alt+click 后需移到另一个浏览器窗口才能触发。
3. 遮罩层会重新出现，无法第二次 Alt+click。

### 根因

- **#3（遮罩重出）**：委托用了 `web_only=False`，扩展在 webOnly=false 下**鼠标一移出
  页面视口就自动报 backToDesktop** → 遮罩重建。用户移动鼠标瞄准第二次点击时稍微划过
  页面边缘即触发。
- **#2（窗口不对）**：委托启动时未 `SetForegroundWindow` 目标浏览器，扩展的
  `launchBrowserCapture` 取「当前活动窗口」的活动标签页，会话开在错误窗口。
- **#1（仍 UIA）**：路由判定本身正常（诊断脚本逐项验证通过），实际未触发属上述
  #2/#3 交互问题掩盖。

### 新方案：hover 自动切换，一次点击

遮罩模式下**鼠标移入浏览器内容区 → 自动隐藏遮罩、进入扩展网页拾取**（扩展自带页面内
高亮，`web_only=False`：鼠标移出页面/按 Tab 自动切回桌面遮罩）；Alt+click **一次确认**
即得 web 元素。移出页面 → 自动恢复遮罩 → 桌面 UIA 拾取。全程一个模式、一次点击、
高亮来源随光标自动切换，消除"先点一下切模式"的割裂。

- `_run_web_session(browser, x, y)`（overlay_mask.py）：卸载吞点击钩子（网页确认靠
  DOM click，钩子必须卸）→ 隐藏遮罩 → `SetForegroundWindow(browser)`（修复 #2）→
  `_capture_via_extension(web_only=False)`；backToDesktop → 恢复遮罩 + 重装钩子返回
  "back" 继续桌面拾取；Esc → "cancelled" 结束。
- hover 节流判定（0.3s 或目标窗口变化）：`_web_capture_target(target, ...)` +
  `_extension_online()`（2s 缓存，离线时不切会话避免启动即失败）→ 进会话。
- 手势兜底：自动切换未触发（竞态/离线）时 Alt+click 浏览器内容区仍委托
  `web_only=True`（粘性会话，不再出现遮罩重出）。
- `overlay.py` 新增 `_extension_online()`（查 /api/extension/status，2s 缓存）与
  `_route_log`（%TEMP%\rpa_capture_route.log，路由诊断）。

## 十、以页面内容框为切换点的自动切换（第十轮定型）

用户确认方向：以**网页的内容框**（渲染宿主视口）作为桌面捕获/网页捕获的切换点，自动切换。

### 与第八轮失败方案的差异（关键）

第八轮自动切换失败在"退出"：进网页会话后，切回遮罩依赖扩展的 mouse-leave 检测
（250ms 防抖 + 点击时机竞争，不可靠）→ 标签栏/工具栏点不动。本轮把**退出控制权收归
遮罩主循环**：

- **切换点精确化**：`_web_capture_target` 改为以 `Chrome_RenderWidgetHostHWND`（渲染
  宿主，其窗口矩形即视口/内容框）为边界 —— 命中渲染宿主 = 在内容框内 → 网页捕获；
  命中框架/其它子窗口（标签栏/地址栏/工具栏）= 外壳 → 桌面 UIA。Firefox 等无渲染宿主
  类退回顶栏启发式。
- **会话内监视光标**：`_capture_via_extension` 新增 `viewport_watch` 回调参数 —— 主循环
  每 50ms 调用一次（实时 GetCursorPos + WindowFromPoint + 内容框判定），返回 False
  立即取消会话并抛 `BackToDesktop`（复用"切回桌面"语义）。不再依赖扩展 mouse-leave。
- **`_cursor_in_viewport`**（overlay_mask.py）：会话期间主循环阻塞在 `_capture_via_extension`
  内，`pt` 不会更新 → 监视器必须自己实时读光标位置（不能读闭包里的旧 pt）。
- hover 命中内容框 → 卸载钩子、隐藏遮罩 → 进入会话（`web_only=True` 粘性，无扩展侧
  干扰）；光标移出内容框 → 自动恢复遮罩 + 重装钩子 → 桌面 UIA。手势分支的委托兜底
  同步带 watch。

### 交互效果

一个「捕获桌面元素」入口，遮罩常驻：光标进浏览器页面内容框 → 自动切网页拾取（遮罩
隐藏、页面内高亮）→ Alt+click 一次确认 → web 元素；光标移到标签栏/工具栏/桌面 →
自动恢复遮罩 → Alt+click → UIA 元素。全程一个模式、一次点击、以内容框为界自动切换。

## 十二、Chrome 捕获后 Edge 捕获模式残留 — 会话退出监视按浏览器比对

用户反馈：在 Chrome 中捕获后，Edge 的捕获模式没有退出。

### 根因

会话退出监视 `_cursor_in_viewport` 只判断"光标是否在**某个浏览器**的内容框内"，不区分
浏览器。从 Edge 内容框移到 Chrome 内容框时，光标仍在 Chrome 的视口内 → Edge 会话的
监视器判定"还在视口内"→ 不取消 → Edge 的 content 捕获模式残留。

### 修复（overlay_mask.py）

- `_cursor_in_viewport` 增加浏览器比对：当前光标所在视口的顶层窗口必须**等于本会话的
  浏览器窗口**（`top == session_holder["browser"]`）才算"仍在视口内"。
- 新增 `session_holder["browser"]`，三处会话启动（hover 自动切换 + 两个手势兜底）前
  设置为当前浏览器顶层窗口。
- 效果：Edge 会话中光标移到 Chrome → 监视器立即判 False → 取消 Edge 会话
  （`exitBrowserCapture` 发往 Edge）→ 遮罩恢复 → Chrome 内容框触发新会话（走 Chrome
  连接）。跨浏览器移动自动切会话，不再残留。
