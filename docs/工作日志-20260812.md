# 工作日志 2026-08-12

## 一、捕获桌面元素无法捕获 Tab / Tab 内文字 — 三层根因全修复

用户报告「捕获桌面元素无法捕获 tab 和 tab 内的文字」，用 winapp 拿到 Windows Terminal 的完整 UIA 结构（TabView/TabItem/内部 Text）作对照。本次共定位并修复三个独立根因，真机（Windows Terminal CASCADIA，OpenCode 窗口）逐层 monkey-patch 复现验证。

### 根因 A：捕获子进程跑在缺 uiautomation 的解释器上

- **现象**：捕获结果只有 Win32 窗口壳（DB 里落库元素 `element_type=win32`、无 uia_path），Windows Terminal 的 tab/TabItem/内部 Text 是纯 UIA 元素（无独立 HWND，全在 `CASCADIA_HOSTING_WINDOW_CLASS` 单窗口内），捕获不到。
- **真相**：`.venv\Scripts\python.exe -m src.runtime.main` 会 re-exec 到 uv 托管的 cpython-3.13 基解释器（`pyvenv.cfg` 的 `home` 指向 uv 目录），该解释器**没有 uiautomation**。`run_gui_picker`/`run_gui_verify` 用 `sys.executable` spawn 捕获子进程 → 子进程 `_uia_dependency_ok()=False` → UIA 通道静默失效。
- **修复**：
  - `commands_router.py`：`run_gui_picker`/`run_gui_verify` 改用 `_capture_python()`（解析到 `.venv\Scripts\python.exe`，带 uiautomation 2.0.29）；删两处不再用的 `import sys`。
  - `_uia.py`：运行时 UIA 命令（pickElementUia/clickElementUia 等）在缺 uiautomation 的解释器下回退加载 `.venv/Lib/site-packages`（`_venv_site_packages()`，校验 `pyvenv.cfg` 主次版本一致防 ABI 不兼容，追加到 sys.path 末尾避免遮蔽）。

### 根因 B：hover 高亮刚进入窗口显示整窗

- **现象**：鼠标从别处移到 Windows Terminal 上，蓝框先框住整个窗口；停下不移动（≤6px）时永远不切到单个 tab。
- **真相**：`run_capture` 里鼠标刚进入窗口（`target != last_hwnd`）用 `_get_window_rect(target)` 显示整窗，UIA 细粒度分支要求「同一窗口内移动 >6px」才触发。
- **修复**：进入窗口分支也立即用 `_get_best_rect(target, pt.x, pt.y)` 做 UIA 细粒度命中；找不到/不可用仍回退整窗（行为兼容）。

### 根因 C：停留几秒后高亮偶发变整窗（无法恢复）

- **现象**：hover 正常框 tab 后，停留几秒蓝框变成整窗且不再恢复。
- **真相**（真机 monkey-patch `show_border` + `_get_uia_rect` 复现）：
  1. `_try_uia_capture` 深搜在 Windows Terminal 上偶发 >3s 超时 → `_blacklist_process` 把 `windowsterminal.exe` **永久**加入 `_uia_skip_exes` → 之后整个会话 `_is_skip_uia` 返回 True，hover/捕获全退化为整窗（拉黑后无法恢复）。实测 run_capture 结束后 `_uia_skip_exes={'windowsterminal.exe'}`。
  2. hover 的 `_get_uia_rect` 深搜偶发 >0.3s（provider 抖动）→ 返回 None → `_get_best_rect` 回退整窗。
- **修复**：
  - `_try_uia_capture` 超时只返回 None（本次降级），**不再永久拉黑进程**。微信族的防卡死由 `_is_skip_uia` 的硬编码 `wechat/weixin/wework` 检测兜底；删除不再使用的 `_blacklist_process`。
  - `_UIA_HOVER_TIMEOUT` 0.3s → 1.5s（深搜有 0.4s 节流缓存，不会每帧阻塞；覆盖 Windows Terminal provider 偶发慢）。

## 二、捕获 hover 整体卡顿（>1s）— hover 查询异步化

用户反馈「桌面元素捕获功能好卡，整体都卡，1 秒以上」。根因：hover 查询 `_get_uia_rect` 每帧开新线程 + `t.join(超时)` **阻塞主循环**；Windows Terminal 深搜遍历整棵 XAML 树偶发 >1s → 主循环（30ms 帧）被 join 阻塞，帧率骤降。此前把 `_UIA_HOVER_TIMEOUT` 从 0.3s 提到 1.5s 进一步加长了主线程阻塞时间（回归）。

- **方案**：hover 异步化——新增 `_HoverWorker` 后台单线程持续查询（worker 线程内 `UIAutomationInitializerInThread()` 一次性初始化 COM，不再每帧创建新线程）；主循环每帧只 `submit` 最新鼠标坐标 + 读 worker 最新结果，**零阻塞**。
- **hover 高亮逻辑重构**：进入窗口/停留/移动统一改为「每帧读 worker 最新结果，结果变化才重绘」（`show_border` 防闪烁）；进入窗口时 worker 未就绪先显示整窗，算出 tab 后下一帧自动切换；停留期间持续用最新结果刷新，不再变整窗。
- **模态态**：`mouse_down`（SetCapture）期间 `_pause_hover_uia()` 暂停查询，松开恢复；捕获结束 `_stop_hover_worker()`。
- **移除**：`_UIA_HOVER_TIMEOUT` 常量与 `_get_uia_rect` 的每帧新线程 + join 阻塞实现。
- **验证**：平滑移动 hover 流畅跟随（tab/关闭按钮/内容区逐帧切换），停留 3s 不变整窗，整窗高亮次数 0；`harness:check` PASSED；capture 测试 4 passed；ruff 增量 0（overlay.py 73 为存量）。
