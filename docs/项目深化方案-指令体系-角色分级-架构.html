① 指令体系：新增指令的直觉化流程 + 命令/LLM 分工 确定性动作用命令固化，推理才走 LLM

核心修正：新增指令流程里，凡是"确定性编排动作"（跑脚本、生成桩、落盘、校验）一律固化为命令，零 LLM；只有真正需要推理的地方（自然语言→定义、写 execute() 业务逻辑、解释校验失败）才让 LLM 介入。这样既不浪费 token，又保证脚本执行可复现可靠。

现状：一条前端可见性低的线性链（含大量确定性动作被 AI 代跑）

commands/<type>.json（唯一事实来源） │ python scripts/generate_commands.py ← 确定性·应固化为命令 ▼ 生成桩文件（Python 桩 + JS handler） │ ▼ Agent 手写实现逻辑（backend/control/desktop 从零；extension 填 JS） ← 推理·LLM │ python scripts/build_content_js.py ← 确定性·应固化为命令 ▼ 重启服务器 → auto_register() 加载 → 验证

问题：① 链条全程靠人工记忆"何时跑哪个脚本"；② 上版把确定性动作也归给 AI，浪费 token 且执行不可靠；③ 缺少把"确定性动作 + 推理动作"编排在一起、且角色清晰的载体。

目标态：命令(确定性) + LLM(推理) 分层

把新增指令切成四步，每步明确标注「命令/LLM」。命令用 rpa_new_command（DSH 工具/斜杠命令）封装，本身只是确定性编排器，内部只在两处才会调用 LLM。

① 定义

LLM + 人确认
  • 说一句话："我想要一个『批量截图』指令"
  • LLM 生成候选 <type>.json 定义 + 参数表，人在表单里勾选/微调
  • 命令 校验：cmd 命名冲突、参数类型合法性、runtime 归类

② 生成桩

纯命令
  • 命令 自动运行 generate_commands.py，产出 Python 桩 + JS handler
  • 零 LLM：脚本执行是确定性的，直接落盘

③ 写实现

LLM + 人把关
  • backend/desktop/control：LLM 写 execute()（@register_handler 参数由桩保证，不手写）
  • extension：LLM 写 JS handler 的 registerHandler 回调
  • 结果命令直接落盘到目标文件；人类复核逻辑正确性

④ 验证闭环

纯命令
  • 命令 跑 build_content_js.py（extension）
  • 命令 跑 handler_validator → 全绿才通过
  • 命令 生成一条冒烟流程并运行
  • 仅当失败需要解释时才回 LLM 给修改建议

命令 vs LLM 的明确边界

步骤方式角色说明
校验定义（命名/参数/runtime）命令配置者确定性 schema 检查，不推理
跑 generate_commands.py命令配置者确定性脚本，AI 代跑无意义且不可靠
写 execute() / JS 回调LLM配置者业务逻辑需推理；@register_handler 参数由桩保证
跑构建 / validator / 冒烟命令自动确定性校验，绿了才过
解释失败原因 / 给修改建议LLM配置者仅失败时才回到 LLM

命令载体设计（rpa_new_command）

rpa_new_command（DSH 工具/斜杠命令 · 纯确定性编排器） │ ├─ 入参：{name, definition(可选 JSON), description(可选)} │ · 给了 definition → 跳过 LLM 定义步骤，纯命令走完 │ · 只给 description → 步骤① 调一次 LLM 生成定义草案 ├─ 步骤①（可选 LLM）→ 生成/合并 JSON 定义 ├─ 步骤②（命令）→ 跑 generate_commands.py 生成桩 ├─ 步骤③（可选 LLM）→ 写 execute()/JS 回调到文件 ├─ 步骤④（命令）→ 跑 build_content_js.py + validator + 冒烟 └─ 输出：每步状态 + 校验报告 +（失败时 LLM 建议）

一句话原则（修正后）

脚本的执行、落盘、校验永远固化为命令（零 LLM）；LLM 只出现在"定义生成"和"写业务实现"两个推理点上，且失败解释才额外调一次。让用户一句"新增这个指令"就能走完，既快又准。

② 三级角色分级：开发者 / 配置者 / 使用者 操作对象依次是 插件 / 指令 / 流程

这三级不是三个页面，而是同一套系统里按"操作对象"划分的三层能力边界。分级的本质是：外层(使用者)所见即所用、零暴露；内层(开发者)保留全部控制面。对应现实：你既是开发者也是使用者，但不同时刻只需要看到对应层。

角色操作对象核心诉求应该看到什么
开发者
plugin		 插件本体（rpa-dsh-plugin） 装/卸/配置插件、看插件托管的后端、调参、看健康 rpa-dsh-plugin 配置、后端托管状态、端口/日志、版本
配置者
command		 指令（command 定义 + handler） 增删改指令、写实现、验证；
AI 生成后可进来微调		 指令定义页、指令分类、参数 schema、generate_commands 结果、validator 报告
使用者
workflow		 流程（一个目录 = 一个流程） 捕获元素 → 拖节点 → 填参数 → 运行看日志 流程 tab、元素库、节点画布、运行日志

分级的落点（建议）

  • 默认入口 = 使用者：打开就是流程 tab，元素库/画布/日志一览无余
  • 指令层收敛到「指令定义」页：配置者/开发者通过独立入口进入，不与流程混流
  • 开发者层=插件管理：DSH 的插件配置 + 插件自带的健康/日志面板
  • AI 角色随层变化：使用者层 AI 帮"生成流程"；配置者层 AI 帮"生成指令"；开发者层 AI 帮"诊断/托管"

避免的坑

  • 不要让使用者看到指令定义/依赖注入细节——会吓退；
  • 不要让配置者每次都被插件部署细节打断——级与级之间的"编排细节"要隐藏到下一层；
  • 三级不物理隔离：同一人可穿越，但界面按对象分层，避免"一个页面塞三种心智"。

关键判断：这三级目前的分界是否清晰？

现状：使用者层（流程 tab）与配置者层（指令定义页）已分开；但 DSH 插件配置（开发者层）与后端托管还没有一个统一的"运维视图"。这是最需要补的一块——给插件加一个"健康 + 托管 + 指令状态"的面板，作为开发者/配置者层的入口。

③ 架构优化：拆分服务 + 明确托管 + 启动提速 现状是单进程 FastAPI，lifespan 串行做了很多启动工作

目标：该拆的独立成服务、明确谁来托管、把"冷启动慢"和"每次改都要重启"这两个痛点解决掉。核心洞察：运行态(执行流程/捕获) 与 管理态(定义/配置) 分离——前者要常驻快，后者可懒加载。

目标是启动加速目标

现有 lifespan（main.py:142-200）串行做了这些：models.init_db() → run_migrations() → auto_register()（扫描 + importlib 全量导入 69+ 指令）→ _populate_local_handlers() → 种子分类 → 种子 AI 应用 → 种子指令 → 加载指令到内存。

优化提升做法
懒加载指令注册 大 auto_register() 不阻塞启动：初次请求命中某指令类时才 import。用 lazy registry 替换全量导入
迁移 & 种子移入后台任务 中 DB 迁移/种子放 asyncio.create_task，/health 先就绪；加 /ready 标记真正可用
AI 应用/指令种子按需同步 小 仅在 DB 为空时同步，避免每次启动都 sync/seed
可选：捕获服务常驻化 中大 P3 server.py 常驻遮罩/钩子/UIA，冷启动只一次（方案已论证）
开发时免重启 体验 捕获类改动 spawn 新进程即时生效（已如此）；后端代码改动仍需重启——文档里明确标注避免混淆

启动提速的核心原则

先让 /health 秒回（进程活着、端口就绪），再把真正"能用"（指令全加载、DB 就绪）挪到 /ready 或后台。插件侧 waitForBackendReady 也从"等进程"升级为"等真可用"，避免 30/60s 未就绪误报。

需要你拍板（按推荐）

1. 插件「健康/运维面板」当前是否最该先做？
推荐：是。它补上分级缺的开发者层，也顺带解决"后端到底起没起/端口多少"这类高频疑问。
2. 指令生成载体：rpa_new_command 命令（已修正，按推荐定为命令）？
推荐：定为确定性命令（如 /rpa new-command 或 DSH 工具）。它内部只在定义/实现两处调 LLM，其余全为固化脚本执行；纯命令路径（已给 definition）可完全不经过 LLM。
3. 捕获常驻化（P3）要不要提前？
推荐：暂缓。当前 476ms 冷启动可接受，先用着；等"高频连续捕获"成为真实痛点再上。
