# 微信 4.x 内部元素自动化 — 方案调研

> 日期：2026-08-14 | 状态：调研完成，暂不改码 | 触发：微信内部元素无法捕获（UIA 只暴露窗口外壳）

## 结论

微信 4.1.12+（含 4.x 全部版本）为**自绘 Canvas UI**（Qt/MMUI 渲染表面），内部控件不暴露给
UIAutomation / MSAA —— UIA 路线**已死**。业界（影刀 RPA、wxauto 系、pywechat、wechatauto 系）
共识与做法：

| 路线 | 原理 | 适用 | 代表实现 |
|---|---|---|---|
| **图像识别** | 截图 → 模板匹配 / OCR 定位坐标 → 鼠标键盘模拟 | UI 操作（点击/输入/列表项） | 影刀"图像库"、wechatauto `guia.py`、cnblogs uiautomation+OpenCV+EasyOCR |
| **数据库直读** | 解密微信本地 SQLCipher 4 数据库（内存提密钥） | 数据读取（消息/联系人/会话/朋友圈） | wechatauto-replica `db.py`（SQLCipher4 解密） |
| UIA（旧） | 无障碍树 | 微信 3.x / 部分 4.x 账号 | 已失效：4.1.12+ 自绘不暴露；实测偶发 access violation 崩溃 |

## 实测证据（本机）

- 微信 4.x = `weixin.exe`，窗口类 `Qt51514QWindowIcon`，子窗口仅 3 个渲染壳
  （`Chrome_WidgetWin_0` / `Intermediate D3D Window` / `MMUIRenderSubWindowHW`）—— 无内部 HWND。
- UIA 探测：`_uia_chain_at` 只返回 `WindowControl '微信' → PaneControl`（外壳）；特定时机
  `ControlFromPoint` **access violation 进程崩溃** + `RPC_E_DISCONNECTED`。
- 结论：`_is_skip_uia` 硬编码跳过 wechat/weixin/wework **应保留**。

## 影刀 RPA 的做法（参考）

官方承认"微信 4.0 版本获取不到元素"（[wiki](https://ying-dao.feishu.cn/wiki/NvxhwyjnViULNpkSdaMcBMJAnNd)）；
社区同样报"只能捕获整个微信窗口、无法深度捕获"（[问答](https://www.yingdao.com/community/detaildiscuss?id=790391994218020864)）。
其桌面自动化三梯队（[教程](https://developer.volcengine.com/articles/7657456522313613363)）：

1. **桌面元素捕获**（UIA/ACC）—— 微信能捕获的场合优先用
2. **图像识别**（捕获不到兜底）：
   - 点击图像 = 模板匹配（截图上传、相似度 0.8、可设偏移）
   - 鼠标悬停在文本上 = OCR 文字定位
3. **键盘模拟**（SendInput）—— 输入框不响应时

微信实战：搜索框/联系人/输入框先元素捕获，**失败用"点击图像（头像截图）"备选**；
发送后随机等待 1-3s 防封控。

**影刀自身短板**（我们可做得更好）：图像识别无区域设置（全屏搜索效率低、易误配）；
分辨率/缩放敏感（要求固定 1920×1080@100%）；建议保留标题栏作参照物、降相似度阈值。

## 对本项目的建议（路线 A：图像识别元素）

与现有架构契合度高，且比影刀多两个天然优势（区域截图 + 虚拟屏坐标体系已在）：

- 新增元素类型 `element_type="image"`：捕获器框选区域 → 存截图 + 可选 OCR 文本 / 模板图 +
  相对坐标 + 窗口锚点
- 运行时执行：限定区域模板匹配 / OCR 定位 → 坐标偏移 → 复用现有 SendInput
  （`_os_move_mouse`/`_os_click`/`_os_type_text`）
- 待调研：OCR 引擎选型（RapidOCR / PaddleOCR / tesseract 的中文识别率与体积权衡）
- 数据类需求（读消息/联系人）另走数据库直读，有合规风险需自行权衡
