要解决这个问题，核心思路是：主循环永远不等待，能拿就拿，拿不到就跳过。

🔍 问题复现：为什么锁会争抢？
看你的代码，_HoverWorker 和主循环之间通过 self._lock 共享数据：

python
# overlay.py:437-462 (简化)
class _HoverWorker:
    def _loop(self):
        while not self._stop:
            self._wake.wait(timeout=0.2)
            with self._lock:                    # 🔴 Worker 持锁
                req = dict(self._req)           # 读请求
            rect = self._query(...)             # 深搜 3.5s（锁已释放）
            with self._lock:                    # 🔴 Worker 再次持锁
                self._res = {"rect": rect}      # 写结果

    def latest(self):
        with self._lock:                        # 🔴 主循环尝试拿锁
            return dict(self._res)              # 如果 worker 在写，主循环等 50ms
问题在于：self._lock 是一个普通的 threading.Lock，主循环调用 latest() 时，如果 Worker 正在执行 with self._lock 写结果，主循环会被阻塞等待，直到 Worker 释放锁。这就是你看到的 timeout=0.05 等待。

✅ 解决方案 1：非阻塞锁（Try-Lock）—— 最小改动，最大收益
主循环改成 “能拿就拿，拿不到就跳过”：

python
def latest(self):
    """主循环每帧读最新结果（非阻塞：拿不到锁就跳过）。"""
    if self._lock.acquire(blocking=False):  # ✅ 不等待，立即返回
        try:
            return dict(self._res)
        finally:
            self._lock.release()
    return None  # 或返回上次的结果
效果：

主循环不再因为锁被占用而等待

帧耗时从 92ms 降回 ~31ms

代价是：如果 Worker 正在写结果，主循环这一帧会继续用旧边框，下一帧再更新

用户感知不到差异（30fps 下，一帧的延迟 ~33ms）

✅ 解决方案 2：无锁数据结构（Lock-Free）—— 更彻底
用 threading 的原子操作或者 queue.Queue 替代显式锁：

方案 2a：用 queue.Queue 做单向通信
python
import queue

class _HoverWorker:
    def __init__(self):
        self._result_queue = queue.Queue(maxsize=1)  # 只保留最新结果
    
    def _loop(self):
        while not self._stop:
            # ... 执行查询
            rect = self._query(x, y)
            # 非阻塞写入：如果队列满了，先清空再写入（只保留最新）
            try:
                self._result_queue.get_nowait()  # 扔掉旧结果
            except queue.Empty:
                pass
            self._result_queue.put_nowait(rect)
    
    def latest(self):
        """主循环读取：非阻塞，拿不到就返回 None。"""
        try:
            return self._result_queue.get_nowait()
        except queue.Empty:
            return None
queue.Queue 内部用条件变量实现，但 get_nowait() / put_nowait() 是非阻塞的，主循环永不等待。

方案 2b：用 ctypes 共享内存 + InterlockedExchange
对于极致性能（C 级原子操作），可以用 ctypes.windll.kernel32.InterlockedExchange 来读写一个简单的整数/指针。但 Python 对象（dict）没法直接放进去，需要序列化。

不推荐：过度设计，收益有限。

✅ 解决方案 3：双缓冲（Double Buffering）—— 读写分离
主循环读的是“上一帧的结果”，Worker 写的是“最新结果”，两者不需要同步：

python
class _HoverWorker:
    def __init__(self):
        self._res_ready = False
        self._res = {"rect": None, "x": 0, "y": 0}
        self._res_backup = {"rect": None, "x": 0, "y": 0}
        self._version = 0
        self._read_version = -1
    
    def _loop(self):
        while not self._stop:
            # ... 执行查询
            rect = self._query(x, y)
            # 写入备份，无锁（Worker 独占写）
            self._res_backup = {"rect": rect, "x": x, "y": y}
            # 原子递增版本号（Python int 赋值是原子的）
            self._version += 1
    
    def latest(self):
        """主循环读取：无锁，仅比较版本号。"""
        ver = self._version
        if ver != self._read_version:
            # 有新数据，读备份（Worker 此时可能正在写，但 Python GIL 保证单条赋值原子）
            self._res = dict(self._res_backup)
            self._read_version = ver
        return self._res
原理：

Worker 独占写 _res_backup

主循环只在版本号变化时才读数据

读操作是 dict(self._res_backup)，这是浅拷贝，耗时纳秒级

完全没有锁

最快见效的做法：在你现有的 _HoverWorker.latest() 里，把 with self._lock: 改成非阻塞获取：

python
def latest(self):
    """主循环读最新结果（非阻塞）。"""
    if self._lock.acquire(blocking=False):
        try:
            return dict(self._res)
        finally:
            self._lock.release()
    # 拿不到锁 → 返回当前缓存（主循环用旧边框，下一帧再试）
    return self._cached_res if hasattr(self, '_cached_res') else {"rect": None}
然后记得在 Worker 写结果时更新 _cached_res：

python
def _loop(self):
    # ...
    with self._lock:
        self._res = {"rect": rect, "x": x, "y": y}
        self._cached_res = dict(self._res)  # 主循环拿不到锁时的兜底
这样改完，主循环的帧耗时会立即从 92ms 回到 ~31ms。
